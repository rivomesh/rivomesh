# RC-03 / RC-08：事务跳过与缺口记录设计草案

状态：待实现。本文件只记录下一步设计，不代表已经提供跳过按钮或接口。

## 边界

首个档案沿用事务型 PostgreSQL/MySQL 目标及原 Agent/日志目录。要求暂停整个任务、原生目标围栏已完成、保留新的完整原始/规范化事务证据。只允许跳过选定订阅的下一完整事务，不修改源 GTID，不删除原日志内容，不影响其他订阅应处理的源事件。

必须先使用 RC-05 核对：已提交的目标事务走确认流程；原生断点越界、内容不一致、历史模式或规范化内容缺失、epoch/错误版本变化均拒绝。断点未前进本身不能证明目标业务数据不存在。需要核对原生目标写入协议和完整事务边界，不能把采集/解码故障假装成目标应用失败。

## 执行与崩溃恢复

目标本地事务同时保存 SKIP 回执、原始事务投影身份及原生安全进度，明确标记结果为 SKIPPED，不能伪造 APPLIED。日志侧保存可恢复的操作计划和持久缺口记录；原生提交成功但日志确认丢失时，必须按原生 SKIP 回执恢复缺口和 ACK。跨系统没有一个共同本地事务，因此每个提交边界均需可重放，不能声称存在跨系统原子提交。

同一操作 ID、证据摘要、目标、原因和操作人必须幂等；参数不同拒绝。先保留原证据和计划，再改变原生断点。目标未能提交 SKIP 时，日志不能提前确认。保持整个任务和目标暂停，并推进目标错误版本，使旧恢复请求失效。

## 旧版本隔离

现有格式3和旧自动 Fanout 只认识 APPLY 断点，不能让其将 SKIP 回执当成普通成功。实施前需明确数据日志/原生元数据格式升级及控制协议准入，整体验证暂停围栏后再升级。旧运行进程必须被 epoch 撤销；旧二进制重开必须在初始化/认领前拒绝新格式。仅增加一个会被旧代码忽略的 outcome 列，不足以证明安全。

## 缺口与界面

缺口至少包含：操作ID、证据ID/摘要、源身份和事务范围、目标/表范围、原因、操作人、确认时间、原生回执、恢复阶段及关联配置/世代。界面必须显示“已跳过、数据存在缺口”，不能显示为无损追平。支持按任务/目标查询，原生提交尚未完成日志确认时显示待恢复；不能删除证据来隐藏缺口。

## 必要验收

- 完整跨表事务、目标数据库映射、空投影/BARRIER及无主键标识边界。
- 真正未提交、已提交、原生序号/摘要/epoch不符三类情况，禁止误跳。
- 目标提交前、提交后响应丢失、日志缺口/ACK提交前后的进程强杀与原操作重试。
- 两个管理员竞争、旧错误版本、权限撤销、旧 Worker 恢复、新旧二进制格式隔离。
- 其他目标仍按原源顺序处理；界面能查到原证据和持久缺口；恢复后明确显示存在数据差异。

## 首个实现决策

- 控制面增加协议7显式准入，要求原成员正常停止；保留协议5审阅及协议6确认的旧配置行为。
- 数据日志格式在第一次有持久计划的跳过中由3单调升级到4，与 PREPARED 计划一起提交。旧发布包的初始化/身份检查必须拒绝4；升级之前先整体暂停并完成 epoch 围栏，撤销旧在途 Worker。
- 原生断点新增仅 SKIP 时非空的标记与回执摘要，普通 APPLY 不改变旧断点的JSON表示。新 Fanout 遇到领先ACK的SKIP必须拒绝普通确认；已经确认的SKIP断点必须能匹配源侧缺口。
- 存在 PREPARED 计划时，恢复任务和恢复相关目标必须拒绝，直到原操作恢复完成或经过受控取消。这样目标已提交/日志未提交时不会被自动循环伪装成APPLIED。
- 对已有格式4日志，计划/缺口表丢失必须拒绝，不能自动建空表掩盖历史；格式3第一次升级只允许增加专用元数据。
- 回执、缺口和原证据保留，当前目标断点推进后仍能按原操作ID重试读取结果；不同参数或另一操作竞争同一事务必须拒绝。
- 首档目标检查受影响表的事务能力、快照完成、结构/所有权和已知依赖，拒绝不明确的触发器/外部副作用。没有完整目标投影或不是明确 TARGET_APPLY 故障时不提供跳过。
