# 缺口核验：共同校验点与原子记录

[English](design-gap-verification.en.md) · [任务](tasks.md) · RC-08 PARTIAL

当前提供内部模型与执行组件，尚未开放管理 API/UI。代表性H2/PG/MySQL内部合同已通过；真实同步链路验收及用户操作闭环完成前，不能将 RC-08 标为完成。

## 审阅范围

核验计划固定一个目标、配置摘要、日志代次、源身份、共同校验点、已封存报告及源数据摘要，最多包含100条已有缺口和1000张相关表。每条缺口必须有完整事务计划与原生执行凭据；涉及表的历史 schema 版本必须与共同点一致。不同源、目标、代次、schema、坐标或不完整/存在差异的报告拒绝生成计划。计划仅包含元数据，不包含业务行值。

历史报告 MATCH 只允许形成审阅计划，不能直接消除缺口。执行时必须重新扫描目标上所有受影响表，使用有界磁盘排序计算行数和内容摘要，与封存的源数据比较；只核对行数或只核对跳过事务的行都不充分。差异、超时、原生断点变化或源暂停围栏变化都不写入核验成功记录。

## 并发与持久化

执行持有源日志任务行锁，从读取原缺口、扫描目标，到提交核验凭据始终不释放。恢复运行、Worker所有权变更以及同步服务的修复写入必须取得同一围栏。旧Worker另受目标原生epoch与共同点约束。各表不需要同时驻留内存。

本机制要求目标业务数据仅由同步服务写入；外部应用或管理员的直接写入不在此围栏内。未来手工补数据入口也必须取得同一围栏，不能绕过它。核验针对封存的历史源共同点，不宣称源当前时刻与目标相等。

源日志增加 `rm3_gap_verification`，并在 `rm3_gap` 保存核验ID与凭据摘要。一次源数据库事务同时写入凭据和全部选定缺口关联；任一步失败全部回滚。保留原始SKIP计划、回执、缺口和报告，不执行目标业务DML，不修改ACK，不恢复运行。

记录状态为 `VERIFIED_AT_COMMON_CUT`，凭据包含原审阅计划、共同点和核验时间。相同请求、相同计划重放返回原凭据；即使任务随后恢复运行，也只返回历史结果，不重新核验。相同请求修改原因或范围拒绝；已核验缺口不能用另一个请求覆盖。重复并发请求应得到同一凭据。凭据丢失、内容变更或关联不完整必须拒绝，不能静默创建空历史。

首版直接创建所需元数据结构，不增加旧开发候选的ALTER/迁移兼容。需要升级测试环境时先核对数据和持久状态，不能只复制游标。参见[首版基线](../../zh-CN/first-release.md)。

## 尚未完成

管理员计划审阅/确认、跨节点持久命令与幂等回执、分页缺口状态及界面操作仍需接入；公开状态必须分别展示原始缺口历史、未处置缺口与指定共同点的核验结果。现有 `hasGaps` 仍表示存在SKIP历史，不能据此宣称核验失败或永久一致。当前内部组件只纳入H2/PG/MySQL事务模型，不扩展承诺到所有SQL、分析库或消息目标。
