# CP-04 管理端 Agent 交接

控制库保存任务归属和命令队列。数据日志保存采集、投递位置和写入租约。替换 Agent 要同时取得两处权威，并能读取原来的受保护恢复资料。使用同一 Agent 目录和身份进行 Pod 换节点另按部署流程处理。

## 准入

新任务自动分配在控制权威锁下预留一次任务容量。迁移需要持久计划，绑定原 Agent、候选 Agent、配置版本、日志指纹和代次，以及任务请求标识。

候选 Agent 验证同一个事务日志库、源日志覆盖、目标和所需密钥，核对恢复所需的报告、证据和操作回执。迁移提交前把候选配置放在未激活的暂存目录，并确认任务槽和 Worker 容量。本地日志任务可以随卷和原 Agent 身份迁移。迁入另一份私有目录需要先验证状态已完整移交。

## 计划交接

1. 保存原请求和预期权威修订，暂缓任务配置写入并记录未结束命令。
2. 排空原 Agent。记录最终采集位置、目标回执、日志租约纪元和期望状态，确认不确定的操作结果。
3. 原租约失效后，在事务日志中激活候选分配代次。Worker 领取和续租时核对该代次，上一代 Worker 无法重新领取。目标协议还要隔离旧 Worker 已发出的写入。
4. 在控制库提交候选绑定。再次核对两处绑定后，按原保存状态启动，保留暂停和停止意图。各入口发布同一归属和租约。

两个存储依次提交，每步都先持久记录阶段和证据。重试使用同一交接标识继续未完成阶段。日志已切换但控制库未提交时，保持隔离并显示交接待完成。此时回退须使用更新的分配代次，并重新验证状态。

## 独立 Worker 的日志准入

[独立任务运行手册](../../zh-CN/pipeline-v3.md#使用-postgresql-日志接管独立-worker) 中的 `init-writer` 和 `transfer-writer` 命令用于验证日志侧写入归属。核对各目标已确认的共同位点后，在同一个 PostgreSQL 事务中持久化交接回执并提高租约纪元。替换 Worker 应用数据前先提高各事务型目标的纪元。原 Worker 即使在两步之间恢复，也没有未处理的业务事务可写，无法凭旧配置修改日志或重新领取租约。

管理端交接还需持久化控制阶段，并验证原操作回执和恢复文档可达。按大小轮转的诊断日志用于运维分析，可通过原 Agent 或归档继续查阅。独立路径要求租约已失效或释放、快照已完成、各目标追平且原日志与目标元数据完整。中途快照、目标不可达、未结案操作和跨库提交恢复仍需要单独验收。

## 故障验收

- 分别在全量阶段和增量提交后停止原 Agent，由合格候选打开原报告和快照继续。
- 日志分配已激活后丢失控制库响应，使用同一请求收口。
- 冻结旧 Worker，完成隔离后再恢复它，验证旧写入和续租被拒绝。
- 日志历史、代次、证据、目标协议或容量不满足时拒绝候选，保留最新记录位置。
- 从两个入口核对权限与历史回执，验证跨节点报告的访问范围跟随任务和节点授权。

新任务分配与运行任务交接分别验收。优先对已验证原生租约隔离的目标试验共享日志交接。

## 证据安装与日志停驻

同库内部接管先绑定唯一签名请求，再执行归属事务。Controller 退出后，另一入口可重放原请求。候选 Agent 确认已安装的配置为 STOPPED，再独立安装原报告和闭合回执。候选重启后，`EVIDENCE_ADOPTED` 回执用于授权只读历史访问。

同一事务停驻日志并切换到对应的 15–18 格式，保留已启用的目标缺口与源排除能力。旧构建在日志身份校验时拒绝新格式。当前构建也拒绝通用恢复和 Worker 领取停驻日志。显式启动需要重新核对候选证据，并在授予唯一写入权前验证每个目标的原生纪元隔离。

### Worker 准入前的目标隔离

独立管理员请求将自身标识和当时的权限修订绑定到签名交接准备记录。候选 Agent 核对原源断点和快照。目标端核对原回执及写入纪元后，在本地事务锁内提高纪元。重试可以接受已处于停驻纪元的目标，前提是原回执和快照仍与签名切点吻合。已提交的隔离回执覆盖全部配置的 SQL 目标。完成后日志继续停驻，等待独立的 Worker 准入步骤。

原生目标校验阶段由 20 秒的共享控制事务守卫约束。校验超时会保留待处理审批，等待期间同一控制库的并行管理操作可能延后。当前证据覆盖限定交接档案。

### 目标隔离后的 Worker 准入

独立管理员请求绑定已提交配置、已接收证据和全部 SQL 目标的原生隔离回执。候选凭当前租约最后核验源断点和目标检查点。共享 PostgreSQL 事务将停驻日志提升到准入格式 19–22，并同时记录签名的 `WORKER_ADMITTED` 回执。原源断点和日志恢复能力保留。较早版本拒绝准入格式。

候选本地注册表原子保存同一请求 ID 和 RUNNING 启动意图，随后在控制库记录 `WORKER_PROJECTED`。共享准入后中断时，候选可以按原回执继续本地投影。Agent 重启先核对本地启动标识、共享写入绑定、交接记录和原生日志格式，再调度 Worker。重放已安装的意图会保留之后的 STOP/PAUSE。独占日志租约继续约束实际写入。

分别验证部分目标隔离、准入前原生检查点变化、候选进程中断、常规停止重启和接管后的源端 CDC。历史读操作继续校验原节点和候选节点授权与签名文件清单。公开归属切换在两个 Controller 使用同一签名绑定和私有就绪核验。自动迁移和网络分区仍须独立验收。

### Controller 中断后的自动续办

原任务已停止并追平，管理员已绑定原执行请求，候选 Agent 已持久化签名的准入回执时，候选可在 Controller 退出后自动续办归属提交。候选开启原密封配置和证据，复核源断点、目标 SQL 回执及原日志租约。提交前在共享 PostgreSQL 控制事务再次复核任务修订、当前管理员授权、原 Agent 与候选 Agent 的绑定及签名切点。归属与停驻日志原子记录，同一请求最多移动一次归属。候选仍保持 STOPPED，可按原审批流程接收只读证据。

此路径要求原 Agent 的控制绑定仍有效，且原日志租约已经释放或过期。源与目标仍处于支持的独占写入配置。含原始采集归档的交接仍需 Controller 显式提交。审批、租约、私有证据或任一原生切点变化时保留原归属，受有效期约束的待处理回执可以重试。Controller 在登记候选请求之前退出、原 Agent 离线自动提升、跨库存储接管与自动开启写入仍需独立流程。

### 独立 PostgreSQL 日志交接

`journal.splitStoreHandoff` 在受管任务初始化时显式启用分库流程。适用范围为独立 PostgreSQL 控制库与日志库、已排空的 MySQL 源任务和已追平的 MySQL 或 PostgreSQL 目标。准备记录仍绑定原任务修订、原生切点、候选目录和私有证据。

1. 控制库先认证并保存 `rmc_split_writer_transfer`，绑定同一执行请求、候选就绪回执和切点。已封存待办保留容量和停止状态，审阅过期后仍可恢复。
2. 日志库以原分配和已确认切点为前提，在原生事务中退休旧分配、提高纪元并停驻候选分配。重复执行要求候选分配、纪元、原分配和切点摘要完全相符。
3. 控制库保存候选归属与相同执行请求，再由候选以 STOPPED 投影配置和接收证据。候选原私有目录重启可继续已封存审批。授权更新后，可由当前有权限的管理员显式重试同一请求。
4. 目标隔离和 Worker 启动各自有审批。日志准入已经提交时，重试再次核对原生目标圈定回执及原源断点，补齐控制库准入和本地启动意图。只有完成控制准入和本地投影的候选会通过正常入口启动 Worker。

未启用选项的独立日志仍支持只读核验和暂存。原 Agent 未排空便永久丢失、日志历史缺失或候选目录损坏时，根据相应的故障档案恢复原证据和节点身份。 [运维流程](../../zh-CN/global-control.md)

### 原 Agent 离线后的已封存切点恢复

现有评估和准备记录可以认证已审查的停机状态、原 Agent 的目录与进程代次，以及候选的归档核验。原 Agent 的控制租约过期后，普通状态观测不再可用。原计划 `PREPARED` 超时可以释放候选容量，原日志归属仍有效。在登记的原 Agent 仍持有任务归属且控制状态为失联、停止或未知时，管理员可以从 `GET /api/tasks/{task}/handoff` 读取 `offlinePreflight`。其中 `authorityMatchesReview`、`historicalDrainedCut` 和 `historicalReportsAndReceipts` 描述留存的历史评估。结果为 `BLOCKED`，并指出尚缺持久冻结或独立留存的完整归档。交接对话框在评估回执中显示这些核对项。历史归档字段缺失或无效时按缺证显示。

拟议路径适用于已排空的 MySQL 任务，控制库和事务日志在同一个 PostgreSQL 数据库内，目标属于现在已验证的事务型 SQL 档案。原 Agent 与已选候选使用不同私有目录。冻结任务时原 Agent 必须仍持有可认证的控制租约。后续恢复的依据是已提交的冻结记录及其精确切点。仅凭租约过期无法建立这些证据。

#### 拟议持久记录

新增 `rmc_task_handoff_recovery_seal`。以 `(cluster_id, task_id, seal_id)` 为主键，每任务序号唯一，并由控制权威根锁保护当前封存记录引用。行中记录 `FROZEN`、`REVOKED` 或 `CONSUMED` 阶段、原稳定请求 ID 和认证封套。封套绑定控制域、任务修订、活动配置版本与摘要、原节点及已选候选的节点/目录/进程代次/控制纪元、审批管理员和授权修订、数据库签发时间、核准截止时间及序号。终态回执记录关闭请求和精确结果。同 ID 不同请求内容拒绝。超过核准截止时间封存仍冻结，后续提交受阻。

封套还认证原生日志分配与流代次、冻结纪元、采集与规范化序号、源位置摘要、已完成的源表及各目标的快照确认，以及每个目标的精确投影回执。所有目标须已确认同一留存序号。封存清单包括验证报告、结案操作回执、签名故障记录，以及原始采集文件与已核验的原始回执。每一类都须有原 Agent 认证的存在或缺失证明。存在的资料需绑定长度、摘要和受保护的归档版本。归档和验证材料必须能在原 Agent 私有目录丢失后独立访问。绑定候选的现有共享归档可提供匹配资料。历史摘要无法证明归档齐全且现在可独立访问。

#### 拟议操作

1. `Seal` 从原有 STOPPED 审查和容量预留开始。在两端 Agent 租约仍有效时导出、认证并暂存完整清单。解决待处理命令和不确定操作结果。在共享 PostgreSQL 事务内核对任务权威修订和精确原生切点，退休原日志租约，将原分配切换到有版本围栏的冻结状态并持久化封存。旧构建、常规领取、续租、恢复及直接 Worker 入口均拒绝此状态。冻结期间拒绝会改变切点的配置和恢复写入。
2. `Review` 核对当前操作者的任务及双节点授权、候选活绑定与容量、完整独立归档、密封 STOPPED 配置。再从原生端验证同一代次、源日志与当前表结构和完成快照、日志回执和各 SQL 目标检查点。证据缺失或有变更时给出明确拒绝原因，维持原任务归属。
3. `Revoke` 使用独立授权请求并绑定冻结修订。原 Agent 可以安全恢复时，须核验其当前控制租约、私有状态和原生切点，再经过更高代次启用。原 Agent 仍离线且归档不足时继续阻止恢复。
4. `Commit owner` 是后续独立授权操作，还要求数据库时钟下原控制租约不存在或已过期。提交前复核封存、原生切点、当前授权和精确候选准入。在同一 PostgreSQL 事务中消耗封存，退休原任务绑定，将候选分配停驻于更高纪元，并更新任务权威。候选安装证据后维持 STOPPED。目标原生围栏及显式 Worker 准入继续控制启用。原 Agent 返回时仍处于该任务退休状态。

验收需覆盖封存事务前后原 Agent 丢失、复制或回滚归档版本、证据类或验证密钥缺失、源与目标回执变化、授权撤销、候选容量变化、提交响应丢失后重放，以及原 Agent 返回。核对两个 Controller 视图、原源位置和两端业务提交记录，并证实旧写入者持续被拒绝。运行中丢失、未完成快照、待确认事务、分库控制和日志以及自动启用写入仍需独立协议。
